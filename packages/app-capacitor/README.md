# App Capacitor

## Supported OS versions

Native releases require iOS 18 or later and Android 12 (API 31) or later.
This is an intentional support-floor change for the embedded PDF viewer: older
versions can no longer install updates of the app, rather than falling back to
an external PDF app. Both staging and production builds use these minimums.

## Test a native subscription

The Capacitor shell already presents the RevenueCat-managed store flow from
Organization Manager → Billing. For the fastest first pass, use the project's
RevenueCat Test Store key as a one-off override; do not replace the platform
keys in `.secrets/prod/shared.env`:

```sh
VITE_REVENUECAT_IOS_API_KEY=test_... ./scripts/dev/runIos.sh
VITE_REVENUECAT_ANDROID_API_KEY=test_... ./scripts/dev/runAndroid.sh
```

The RevenueCat offering contains Solo, Team 5, and Team 10 Test Store products,
so this path can exercise fixed-tier package loading, the purchase sheet, entitlement
activation, cancellation, and restore without App Store Connect or Play Console
setup. The Test Store key must never be used for an App Store, TestFlight, or
Google Play release.

To test the server-side billing activation too, point the build at staging and
set `REVENUECAT_ALLOW_SANDBOX_EVENTS=true` in staging's `app.env` before its API
Worker deploys. Production intentionally ignores sandbox grants. Full setup and
the real Apple/Google sandbox checklist are in
[`revenuecat-native-stores.md`](../../docs/developer/revenuecat-native-stores.md).

## Releases

Store releases run through fastlane from this package, in the layout, lane
names, and secrets that a2f0/matrix's
[fastlane standard](https://github.com/a2f0/matrix/blob/main/docs/fastlane.md)
sets for every repository. Install the repo-managed tools and Ruby gems once:

```sh
mise install
cd packages/app-capacitor
bundle install
```

### Tiers

`NATIVE_RELEASE_TIER` selects the tier and defaults to `production`; an unknown
tier fails before any lane runs. `fastlane/lib/native_release_target.rb` owns
the table, and the Appfile reads its app identifier, so set the tier in the
environment rather than as a lane option:

| Tier | Native app identifier | Android variant | iOS scheme / configuration | Secrets |
| --- | --- | --- | --- | --- |
| `production` | `com.tearleads.app` | `release` | `App` / `Release` | `.secrets/prod/` |
| `staging` | `com.tearleads.staging.app` | `staging` | `App-Staging` / `Release-Staging` | `.secrets/staging/` |

Both iOS schemes are committed and shared so fastlane can archive either tier
without relying on Xcode's local autogenerated schemes. Android staging
inherits the release build type and uses the same upload key as production;
its separate application ID and Play app provide the store isolation. Before
the first staging upload, follow the canonical
[RevenueCat native staging setup](../../docs/developer/revenuecat-native-stores.md#dedicated-staging-store-apps).
It covers the tier-isolated public SDK keys, fail-closed environment rules,
Google Play access, and App Store signing profile.

### Lanes

| Lane | Does | Options |
| --- | --- | --- |
| `ios build_release` | Signed App Store IPA, without uploading | `build_number:` |
| `ios upload_release` | `build_release`, then uploads to TestFlight | `build_number:` |
| `ios profiles` | Creates or renews the match App Store profiles | `force:true` regenerates them |
| `ios fetch_profiles` | Installs the match App Store profiles read-only | |
| `android build_release` | Signed release App Bundle, without uploading | `build_number:` |
| `android upload_release` | `build_release`, then uploads to a Google Play track | `build_number:`, `track:` (`internal`), `release_status:` (`completed`) |
| `android build_debug_apk`, `android build_release_apk` | Builds an APK for sideloading | |
| `android install_debug`, `android install_release`, `android sideload` | Builds and installs an APK on a connected device | `sideload`: `build_type:` (`debug`) |
| `android test`, `android clean` | Runs the Android unit tests, or cleans the build | |
| `store_build_numbers` | Prints the latest build numbers in both stores | See [store build numbers](#store-build-numbers) |

`build_number:` is the iOS build number or the Android version code; without
it, the lane picks one as described in [build numbers](#build-numbers). Only a
release runs the lanes that upload or change match profiles (`upload_release`
and `profiles`).

Each routine lane has a package script named `<platform>:<lane in kebab case>`,
with a `:staging` variant for the store lanes. Each script sets
`NATIVE_RELEASE_TIER` itself, and arguments pass through to fastlane:

```sh
bun run ios:build-release                # fastlane ios build_release
bun run ios:upload-release:staging       # NATIVE_RELEASE_TIER=staging
bun run android:build-release build_number:1234
bun run android:install-debug
bun run store:build-numbers:staging
```

The scripts are `ios:build-release`, `ios:upload-release`, `ios:profiles`,
`ios:fetch-profiles`, `android:build-release`, and `android:upload-release`,
each with `:staging`; `android:build-debug-apk`, `android:build-release-apk`,
`android:install-debug`, `android:install-release`, and `android:sideload`; and
`store:build-numbers` with `:staging`.

The repository-root wrappers run the store lanes with release guards:

```sh
./scripts/release/buildIosRelease.sh             # ios:build-release
./scripts/release/uploadIosRelease.sh            # ios:upload-release
./scripts/release/buildAndroidRelease.sh         # android:build-release
./scripts/release/uploadAndroidRelease.sh        # android:upload-release
./scripts/release/buildIosStagingRelease.sh      # and the other Staging wrappers
```

All of them delegate to `scripts/release/nativeRelease.sh`. They default
`VITE_API_BASE_URL` to the tier's API (`https://api.tearleads.com` or
`https://api-staging.tearleads.com`), reject a dev-only or cross-tier API or
WebSocket URL and a RevenueCat Test Store or wrong-store key, and let upload
wrappers default to the store's next build number. Pass `--help` for their
options.

### Secrets

The lanes read `.secrets/<secrets tier>/`, the clone's link into
`../matrix-secrets/tearleads/`, unless `NATIVE_RELEASE_SECRETS_DIR` names
another folder; a relative path resolves against this package, and Gradle and
the native web build read the same folder. They load `shared.env` and then
`app.env`, which wins, never override a variable already in the environment,
and import only these names, because both files also hold server values:

- Store credentials and signing passwords: `TEAM_ID`,
  `APP_STORE_CONNECT_KEY_ID`, `APP_STORE_CONNECT_ISSUER_ID`, `MATCH_GIT_URL`,
  `MATCH_GIT_BASIC_AUTHORIZATION`, `MATCH_PASSWORD`,
  `ANDROID_KEYSTORE_STORE_PASS`, and `ANDROID_KEYSTORE_KEY_PASS`. Values copied
  from `root/root.env`, including both keystore passwords today, stay in
  `shared.env` until they are rotated into `app.env`.
- The tier's Vite client settings. Production reads its RevenueCat keys and
  other declared `VITE_*` settings from `shared.env`, never from the
  server-oriented `app.env`. Staging reads only `VITE_REVENUECAT_SYNC_ENTITLEMENT`
  from `shared.env` and only its RevenueCat client settings from `app.env`; see
  the staging setup above for its fail-closed key checks.

The folder also holds `AuthKey_<APP_STORE_CONNECT_KEY_ID>.p8` (App Store Connect
API key), `google-play-service-account-admin.json` (Google Play publishing
service account), and `tearleads-upload.keystore` (Android upload key).

### Build numbers

By default, each store build number is the latest PR merged today, discovered
with `gh` first and from local squash-merge commit subjects like `(#1365)` as a
fallback. When the store's credentials are available, the lane also checks the
store and uses the larger of the merged PR number and the store's next number:
on Android, the configured Google Play tracks and every bundle uploaded to the
app, since Play rejects a version code it has seen even outside a track; on iOS,
the latest TestFlight build for the target app version.

| Setting | Android | iOS |
| --- | --- | --- |
| Explicit number | `build_number:` or `ANDROID_BUILD_NUMBER` | `build_number:` or `IOS_BUILD_NUMBER` |
| Store's next number | `next_google_play:true` or `ANDROID_RELEASE_NEXT_GOOGLE_PLAY=true` | `next_testflight:true` or `IOS_RELEASE_NEXT_TESTFLIGHT=true` |
| Merged PR | `merged_pr_number:` or `ANDROID_RELEASE_PR_NUMBER` | `merged_pr_number:` or `IOS_RELEASE_PR_NUMBER` |
| Merge date | `merged_date:YYYY-MM-DD` or `ANDROID_RELEASE_MERGED_DATE` | `merged_date:YYYY-MM-DD` or `IOS_RELEASE_MERGED_DATE` |

`ANDROID_VERSION_CODE` and `APPLE_BUILD_NUMBER` are still read as fallbacks for
the explicit number. The iOS app version comes from the Xcode target's
`MARKETING_VERSION`; override it with `version:<version>`, `IOS_VERSION`, or
`APP_STORE_VERSION`.

### iOS releases

`ios build_release` runs a release Capacitor sync, verifies that the generated
native config is fully bundled, renders the icon and splash images, and builds
`ios/App/output/Tearleads.ipa` (staging: `ios/App/output/staging/`). It
installs the App Store certificate and profile read-only from match into a
throwaway keychain, deleted whether the build succeeds or fails, and signs the
App target manually. The keychain is the default while the build runs, and the
previous default comes back afterwards, even when the throwaway keychain is
already gone. Signing needs a team ID from `team_id:`, `IOS_TEAM_ID`,
`APPLE_TEAM_ID`, `DEVELOPMENT_TEAM`, `FASTLANE_TEAM_ID`, or `TEAM_ID`.

The archive resolves Swift packages only from `Package.resolved`
(`-disableAutomaticPackageResolution`), and the lane refuses to build or return
the IPA while that file differs from `HEAD`. Its `originHash` covers the
checkout's absolute path, so automatic resolution against a stale local package
cache can otherwise upgrade pins within the manifests' version ranges.

`ios upload_release` uploads with the App Store Connect API key
(`APP_STORE_CONNECT_KEY_ID`, `APP_STORE_CONNECT_ISSUER_ID`, and the `.p8` in the
secrets folder, or the path in `APP_STORE_CONNECT_API_KEY_KEY_FILEPATH` or
`APP_STORE_CONNECT_KEY_FILEPATH`). It uploads only by default, without waiting
for build processing or submitting for review. Set `TESTFLIGHT_CHANGELOG` or
`changelog:` to provide "What to Test". External distribution is off by
default; enable it with `TESTFLIGHT_DISTRIBUTE_EXTERNAL=true` or
`distribute_external:true` and provide comma-separated `TESTFLIGHT_GROUPS` or
`groups:`. External distribution waits for processing, since TestFlight
distributes only a processed build, and submits for review.
`TESTFLIGHT_SKIP_WAITING_FOR_BUILD_PROCESSING` or
`skip_waiting_for_build_processing:`, and `TESTFLIGHT_SKIP_SUBMISSION` or
`skip_submission:`, override either default; skipping the wait distributes
nothing.

`ios profiles` creates the tier's App Store profile in the match repository
with the API key, reusing the team's distribution certificate there, or renews
one that is missing or invalid; `force:true` regenerates it, as after the
bundle ID's capabilities change. `ios fetch_profiles` only verifies and
installs the existing profile.

### Android releases

`android build_release` requires `tearleads-upload.keystore` and both keystore
passwords, runs a release Capacitor sync, and builds
`android/app/build/outputs/bundle/release/app-release.aab` (staging:
`bundle/staging/app-staging.aab`). It prints any generated upload companion
assets, such as `mapping/release/mapping.txt` and
`native-debug-symbols/release/native-debug-symbols.zip`.

`android upload_release` uploads the AAB and those companion files with
`google-play-service-account-admin.json` (or `GOOGLE_PLAY_JSON_KEY_FILE` /
`SUPPLY_JSON_KEY`), skipping Play metadata, changelogs, images, and
screenshots. The track defaults to `internal`; override it with `track:` or
`GOOGLE_PLAY_TRACK`, and the release status with `release_status:` or
`GOOGLE_PLAY_RELEASE_STATUS`. Validate without committing the Play edit with
`validate_only:true` or `GOOGLE_PLAY_VALIDATE_ONLY=true`.

### Android sideload

Build and install the debug APK on a connected device or emulator:

```sh
bun run android:install-debug
ANDROID_SERIAL=<device-id> bun run android:install-debug
```

Set `ANDROID_SERIAL` when more than one is attached. `bun run
android:install-release` runs a release Capacitor sync first, which clears any
live-reload URL from the generated native config; `bun run android:sideload`
picks either with `build_type:` or `ANDROID_BUILD_TYPE`. Release APKs use the
tier's upload keystore when it exists and both passwords are set, and otherwise
the debug signing config, so they can still be sideloaded locally. These lanes
do not load the secrets folder, so export both passwords to sign with the
upload key.

### Store build numbers

Print the latest remote build numbers from Google Play and the App Store:

```sh
bun run store:build-numbers
```

The lane uses the secrets folder's Google Play service account and App Store
Connect key; missing credentials or one store API failure do not block the other
lookup. It queries the standard Play tracks (`production`, `beta`, `alpha`, and
`internal`) and the app's uploaded bundles, and reports the highest version
code. Narrow the tracks with `google_tracks:internal,beta` or
`GOOGLE_PLAY_TRACKS`, or one track with `track:` or `GOOGLE_PLAY_TRACK`. Query
TestFlight state instead of the live version with `apple_live:false` or
`APP_STORE_LIVE=false`, and skip a store with `skip_google:true`
(`SKIP_GOOGLE_PLAY`) or `skip_apple:true` (`SKIP_APP_STORE`).
`scripts/release/getCurrentAppStoreBuildNumbers.sh` wraps it for the App Store
builds of both tiers.
