# TLA+ Audit — September 2026

This is a historical snapshot of base commit `3ee12e8367d375ee50dcf7d81adbb79601bf833d`
plus the audit changes described below. Counts are measurements for this audit,
not a live coverage dashboard.

## Assessment and Scope

The suite is a useful bounded protocol regression suite. It has real concurrent
interleavings, explicit trust assumptions, pinned TLC tooling, executable
negative controls, and several bridges to production. It is not a proof of the
complete protocol or its implementation. The main remaining weakness is uneven
evidence that each modeled guarantee is exercised and corresponds to runtime
behavior, rather than TLA+ syntax or missing registry entries.

This audit inspected all 22 TLA+ modules (21 domain models and one trace-export
wrapper), their 23 original configurations, the model registry/checker, negative
control machinery, and the documented implementation boundaries. All 23
original configurations passed TLC. The changes add one progress configuration
and six negative controls, bringing the totals to 24 and 71. No production
vulnerability was established by this model-focused audit.

## Findings Addressed

1. **Raw-history recovery had no automated fault controls.** Its 16 registered
   invariants checked preservation, exact history, generation ownership, and
   publication, but no negative control exercised them. Four new controls
   remove the final generation guard, record/checkpoint winner guard,
   checkpoint retirement, or resumed writer's fence check. Each must produce
   its specific invariant violation. A resumed writer restores its stale
   pre-recovery checkpoint when its guard is disabled; the control checks
   durable-history contents, independently of the writer's status label.
2. **Raw-history recovery had no progress obligation.** A worker stalled after
   verification could satisfy all safety invariants. A separately bounded
   configuration now checks eventual success or explicit failure under weak
   fairness of the recovery worker. A fifth control suppresses publication and
   must produce a temporal counterexample without relying on outside activity.
3. **Root priming tested the scheduling flag but not the eventual-sync claim
   independently.** A sixth control selects `DocumentEventuallySyncs` alone
   after removing reprime-on-acknowledgment. Its temporal violation cannot be
   hidden behind the existing, earlier safety failure.
4. **The overview overstated non-vacuity coverage.** It now says controls test
   selected properties' sensitivity to faults. A mutation that violates one
   property does not establish reachability or meaningfulness of every other
   property in that model.

The larger raw-history safety state graph is preserved: 7,749,072 generated and
4,408,696 distinct states at depth 14. Progress uses two updates instead of three
and explores 292,008 generated and 168,712 distinct states at depth 13. All other
model behaviors are unchanged. The new switches are model fault injection,
not runtime feature flags.

## Valuable Remaining Work

### 1. Independent recovery traces and success witnesses

Extend the existing implementation-to-model projection pattern to
`RawHistoryRecovery` and `DeferredTailSettlement`. Record races at actual SQL
claim/completion, generation replacement, settlement, and recovery installation
seams. Replay both successful and refused traces, including reset immediately
before install and a waiting writer resuming immediately afterward.

Add explicit reachability witnesses for successful publication, queued-row
settlement, stale completion, and checkpoint retirement. Mutation controls
demonstrate a failing path after a rule is removed; they do not guarantee that
the intended successful path remains reachable with all production rules on.
The abstraction-map linter checks identifier existence, not semantic equivalence
between an action and its implementation. This is the highest-value next step.

### 2. Grant and keyring independence

Add controls for `ContainerGrantScope`'s organization restriction, active-user
requirement, and roster-removal blocker. Split grant preparation and roster
removal into transaction phases if the intended claim includes serialization;
currently the model assumes those operations are atomic.

For `KeyringReachability`, validate closure with an independent small graph
oracle or production trace replay. Its properties share `Closure` with recovery
and assume every current member already holds the current KEK. Model missing
current recipient wraps separately from missing historical wraps. Add a
revoked-member knowledge set if claiming future-key confidentiality: excluding
revoked members from recovery queries does not prove they cannot derive keys.

### 3. Progress beyond a finite successful worker

Add eventual settlement to `DeferredTailSettlement`, with explicit assumptions
about responses, retries, absence of perpetual reset/relink, and durable queue
completion. Its existing eight action properties establish safety, not eventual
delivery. Keep safety checks free of fairness assumptions that might conceal
an invalid durable transition.

Extend raw-history progress with retry, cancellation, and network-failure
phases before claiming recovery under those conditions. The new progress
check assumes awaited operations return and proves termination, not that every
input succeeds. `RestartProbeConvergence` and honest `NoBrickedDevice` have
monotone bounded versions, so their eventual convergence checks necessarily
reach a quiescent server; they do not prove catch-up under unlimited writes.

### 4. Broader bounds with recorded coverage

Introduce a separate scheduled registry with bounds chosen to expose additional
behaviors: repeated restart/reconnect, more than one outstanding mutation,
additional independent peers, multiple documents in a restore, and longer
revocation/keyring histories. Keep the small pull-request registry. Record
per-configuration bounds, action coverage, state counts, depth, and elapsed time
as artifacts so dead actions and accidental state-space reductions are visible.
The two largest models already dominate the suite; simply increasing every
constant is less useful than targeting a missing interleaving.

### 5. Narrow unbounded proofs and explicit exclusions

The closure and vector-dominance rules are candidates for small inductive
proofs independent of TLC's finite bounds. Such proofs would still need a
refinement argument to establish runtime correctness.

Keep exclusions prominent: cryptography and SQL atomicity are abstracted;
`NoBrickedDevice` stops following a device after an undetectable forged branch;
many models include an always-enabled stuttering action, so a clean TLC
deadlock check is not evidence of useful progress. The expected meaning of
termination, deadlock, invariants, and temporal checks is described in the
[TLC model documentation](https://nightly.tlapl.us/doc/model/overview-page.html).

## Reproduction

```sh
bun run check:protocol-models
bun run check:protocol-negative-controls
bun run check:protocol-traces
bun run check:protocol-projection
bun run check:no-brick-projection
bun run lint:formal-maps
bun run test:protocol-models
bun run test:protocol-conformance
```

These checks are also included in the repository's normal gates. Passing them
supports the bounded claims and bridges listed above; it does not erase the
remaining boundaries.
